## Contract

Schema v3 adds `tasks`, `task_dependencies`, `assignments`, and `task_events`. Task fields are immutable except state/version. Event sequence is monotonic and database-global. Update/delete triggers guard dependency edges, snapshots and event history. The engine does not expose SQL, history edits or deletion. Timestamps are UTC. The schema migration and user_version advancement share ORB-005's write transaction.

All endpoints require the existing session bearer token:

- `POST /v1/tasks`: `{project_id, title, acceptance, dependencies?: string[]}`, returns 201 queued/version 0 plus dependencies, assignments and events.
- `GET /v1/tasks?project_id=...`: insertion-ordered tasks in that registration, including full history. Unknown project returns an empty list. `GET /v1/tasks/{id}` returns details or 404.
- `POST /v1/tasks/{id}/assignments`: `{expected_version, agent_id}`; only ready tasks can be assigned, moves to assigned and snapshots Agent in the same transaction. Missing agent is 404.
- `POST /v1/tasks/{id}/transitions`: `{expected_version, state, note, reviewer_id?, human_approval?}`. Version/state/dependency/policy conflicts are 409; malformed input is 422, missing task/reviewer is 404. Unknown input fields are rejected.

Transition table (assignment is a dedicated action):

| Source | Legal targets |
| --- | --- |
| queued | ready, blocked, cancelled |
| ready | blocked, cancelled; assignment → assigned |
| assigned | running (worker only), blocked, failed, cancelled |
| running | awaiting_review, blocked, failed, cancelled (all worker only) |
| awaiting_review | awaiting_approval (independent review), ready (review rejection), blocked, cancelled |
| awaiting_approval | completed (explicit human approval), ready (revision), blocked, cancelled |
| blocked | ready, failed, cancelled |
| completed, failed, cancelled | none |

The internal store method requires `execution=True` for entry to running/awaiting_review and all running-state changes. HTTP cannot set this flag. Awaiting review requires nonempty bounded artifact references `{label, reference}` in the transition; these are stored as audit metadata, never opened or executed. Review accepts/rejects with a configured reviewer ID distinct from every prior assignment author and snapshots that reviewer against the latest assignment ID. Completion requires a strict boolean human approval and an audit note. Every revision returns through ready and a new immutable assignment; prior approval does not allow a shortcut to completed. This API never merges Git or executes a model.

Desktop users select/register a project, explicitly refresh its tasks, create a task with acceptance criteria and existing dependencies, mark it ready, choose a configured agent and assign it. Detail shows acceptance, dependencies, assignment summary and ordered audit history. Conflicts retain drafts and ask for refresh. Connection/project changes clear task state; pending task requests disable project/connection switching. Execution/review/approval controls are intentionally absent until real execution evidence is available.

## Boundaries and remaining gaps

This is task/assignment metadata, not a verified complete local mission. No configured agents are fabricated. No worker, lease, scheduler, worktree creation, subprocess, live cancellation, actual diff generation, model/cloud job, model download, public listener, credential access or merge is introduced. No dependencies/lockfiles changed; existing local environments are reused. Frontend handler tests are not native connected or browser layout smoke tests; the native build and end-to-end task flow are not claimed here.

Assignment snapshots contain the Agent profile only. Skill entries remain user-configured references with no verified immutable skill registry behind them; tool entries are configuration, not runtime grants. Worktree binding is not yet available and is explicitly deferred to ORB-007's execution/run contract; this PR does not claim a worktree or executable assignment is ready. Execution must revalidate project identity/root, bind an isolated worktree and enforce permissions independently. This metadata API accepts stored registrations without probing the filesystem.

Reviewer ID and human approval are assertions made by the trusted local session-token holder, recorded with evidence notes. They are not independent agent authentication or a multi-user authorization system. Future workers must not receive this user session token or ability to approve their own work; distinct scoped worker credentials and actual review/approval UX are future integration requirements. Artifact references are user/worker assertions, not proof of file integrity. No automatic task completion or Git integration is enabled.
